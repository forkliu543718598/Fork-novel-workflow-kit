# 03 创作 ↔ 审核循环（DeepSeek ↔ Gemini loop）

## 角色分工

- **写稿角色**（作者当前用 DeepSeek / WorkBuddy 自带 4.1-flash）：按本章 spec 写正文。选它的理由是积分便宜、前期基本不花钱，适合海量正文。
- **审核角色**（作者当前用 Gemini）：逐项审核，给 PASS/FAIL 和具体修改点。**不能和写稿角色相同**。

## 单章循环

```
第 N 章 spec
   │
   ├─ 写稿：prompts/02 → 正文草稿
   │
   ├─ 审核：prompts/03 → PASS / FAIL + 问题清单
   │
   ├─ FAIL：prompts/04 限次修订 → 回到审核
   │
   └─ PASS：写回 Obsidian → 第 N+1 章
```

## 审核的六个维度

审核角色必须逐项给结论，不接受"整体不错"这种空话：

1. **剧情连贯性**：是否承接上一章、spec 里的核心事件是否落地、有无突兀跳跃。
2. **设定冲突**：是否违反世界观/人物设定/边界（如无系统外挂、主角不该知道的信息）。
3. **人物表现**：性格是否走形、对话是否是这个人物会说的话。
4. **文字质量**：网文节奏、有无机械 AI 腔、重复啰嗦。
5. **用户硬性要求**：spec 里的爽点、笑点、章末钩子是否覆盖。
6. **平台合规**：是否含推广引流（联系方式/外链/邮箱域名）、敏感内容、字数是否达标。

## 限次修订

- 约定最多 **N 轮**（建议 2–3 轮），防止来回扯皮。
- 每轮修订只针对审核列出的问题，不重写整章。
- N 轮仍 FAIL → 升级给人工或策划角色重出 spec。
- 每章审核记录留档：轮数、判定、问题清单、最终结果。模板 `templates/审核记录模板.md`。

## 为什么写审必须分离

同一个角色写完自己审，等于"自写自夸"，会系统性漏掉设定冲突和 AI 腔。
作者实战中，两部书 326 章都有独立审核记录，最终全 PASS；
后来平台驳回的两处问题（推广引流、格式横线）属于**平台规则维度**，是人工事后发现的——
所以审核维度里专门加了"平台合规"一项，见 `10-平台实战踩坑.md`。

## 省钱与提速

- 正文交给便宜模型（如 4.1-flash 类），审核交给结构能力强的模型（如 Gemini）。
- 写稿角色每次只吃"上一章正文 + 本章 spec + 人物卡 + 伏笔台账"，不吃全书，省 token。
- 批量生成 spec 可以一次做完，逐章循环只跑写审两步。
