# 09 闭环、巡检与数据回流

## 什么是"闭环"

一条完整闭环是：**想法 → 大纲 → 写审 → 知识库 → 提交 → 核对写回 → 数据/异常 → 反哺下一轮大纲**。

只做到"提交成功"是**半闭环**：书上去了，但不知道好不好、有没有被驳回、下一本怎么改进。

## 作者实测的闭环状态

| 环节 | 状态 | 说明 |
|---|---|---|
| 创作 → 审核 → 保存 | 已闭合 | 章数齐全、审核记录全 PASS、原稿保留 |
| 提交 → 核对 → 写回 | 已闭合 | 平台全量核验无缺章、台账/验收落盘 |
| 异常 → 整改 → 复核 | 已闭合但**被动** | 驳回和格式异常都是人先发现的 |
| 数据 → 反哺创作 | **未闭合** | 未接阅读/收益/追读数据 |
| 异常自动发现 | **未闭合** | 没有定时巡检 |

## 补法一：定时巡检（推荐先做）

用 `automation` 或定时任务，每天做一次只读核对：

1. 查作家后台"消息通知"里的审核提醒/驳回。
2. 查章节管理页各状态数量变化。
3. 抽查章节格式：标题长度、是否含外链/联系方式、正文有无多余分隔线。
4. 有异常 → 写待办清单，等待决策；**不自动整改、不自动重提**。

提示词见 `prompts/06-巡检与复盘.md`。

## 补法二：数据回流

1. 定期从作家后台数据中心导出：阅读量、追读、完读率、收益。
2. 让主 Agent 做"追读—完读—收益"周报/月报。
3. 把结论反哺到下一轮大纲：哪些桥段留存高、哪些章掉读、题材是否要调整。
4. 数据留在本地，不进公开仓库。

## 补法三：审核角色回归

作者复盘：两轮平台整改（推广引流、格式横线）是主 Agent 自审自改，
**没有走 Gemini 限次修订**，不符合"审核必须 Gemini"的原始定义。
后来者若严格按本流程，应在整改后也退回审核角色过一遍。

## 待办要显式挂起，不要假装完成

- 因审核锁定无法修改的标题 → 记录"待审核通过后可编辑"，不删重建。
- 完结申请被驳回 → 记录"需本人确认后 N 天重申"，不自行重复申请。
- 任何未落地的动作 → 明确写"未产出"，不拿"文件存在/草稿能解码"当验收通过。
